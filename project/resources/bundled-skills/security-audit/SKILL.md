# 代码安全审计

目标是把「可能被利用的问题」按风险排序交给人，而不是堆一份扫描器原始输出。

## 何时用

- 用户说「审查代码安全」「找漏洞」「上线前检查」。
- 引入新依赖、处理鉴权 / 上传 / 反序列化 / SQL / 模板等重点路径后。
- 准备开源或交付前检查密钥泄露。

## 工具组合

| 工具 | 覆盖 | 说明 |
|---|---|---|
| Semgrep | 源码规则：注入、路径穿越、SSRF、不安全反序列化、弱加密 | `--config p/default`，关闭指标上报 |
| Trivy | 依赖 CVE、IaC 配置、容器镜像 | `fs` 模式，只看 HIGH / CRITICAL |
| gitleaks | 密钥与凭据 | 报告脱敏，不打印明文密钥 |
| Bandit | Python 专项 | 项目含 Python 时追加 |
| gosec | Go 专项 | 项目含 Go 时追加 |

在 Pi 工作台的「安全 → 代码审计」里选择目录即可，结果写入本地报告；也可在命令行直接运行同样的组合。

## 流程

1. 确认审计范围：目录、排除项（`node_modules`、`dist`、`build`、测试夹具）。
2. 先跑 Semgrep 与 gitleaks，再跑 Trivy；Trivy 首次需要下载漏洞库，失败不阻塞其它结果。
3. 统一发现格式：`工具 / 规则 / 严重级别 / 标题 / 文件 / 行号 / 说明`。
4. 去重：按 `工具 + 规则 + 文件 + 行号` 合并，同一位置的重复命中只保留最严重。
5. 误报复核，逐条判断：
   - 是否是测试代码、示例、生成代码或已禁用的分支。
   - 数据是否真的能从不可信输入到达该点。
   - 是否已有上游校验、参数化查询或框架保护。
   - 无法确认时标为「待人工确认」，不直接删除。
6. 排序：critical → high → medium → low → info；同级按可利用性排序。
7. 交付：Markdown 摘要 + SARIF（CI/IDE）或 JSON（二次处理）。

## 报告结构

1. 结论：整体风险等级、最需要先修的 3 条。
2. 发现表：级别、位置、一句话风险、修复建议。
3. 逐条详情：触发条件、影响、证据（代码片段）、修复方式、参考。
4. 已排除项：哪些命中被判定为误报及理由。
5. 扫描覆盖：工具与版本、规则集、未扫描的目录。

## 修复建议原则

- 优先给最小改动：参数化查询、白名单校验、转义、权限检查。
- 密钥类问题：立即轮换，再从历史提交清理；不要只删当前文件。
- 依赖漏洞：升级到修复版本；无法升级时给出缓解措施。
- 不为了消除告警而删除检测规则或加全局忽略。

## 禁止

- 不在未授权目标上运行扫描。
- 不回显完整密钥、令牌或个人信息。
- 不把扫描器输出直接当成定论；高风险结论必须给出证据链。
- 不提供漏洞利用代码或攻击脚本。

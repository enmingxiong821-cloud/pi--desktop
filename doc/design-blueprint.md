# Pi 终端优先桌面工作台：产品设计蓝图

**状态：当前权威设计基线（需求塑形阶段，不是已经实现的承诺）。** 用户已明确选择原生 Pi 终端优先、Electron 方向，并新增按项目需要自行调用 Skills 和 MCP 的要求。本蓝图将已确认事项与待验证方案分开，后续实现或设计变更应更新 [`decisions.md`](decisions.md)。

## 1. 产品目标

为 Windows 开发场景提供一个不必从空终端手动配置的 Pi 工作台：打开项目后运行真实的 Pi TUI；图形侧栏辅助管理项目、模型和能力；Pi 仍负责会话、Agent 循环、原生工具、扩展和执行。

### 产品主张

> 终端是执行事实源，图形界面是项目与能力控制面。方便入口不能变成另一个会话引擎，也不能静默删掉 Pi 的能力。

### 首批验证对象

- Windows 上使用 Pi 开发项目的用户。
- 有多个项目/模型/Skills/MCP 配置、希望按当前工作获得合适能力的用户。

首版先证明“启动真实 Pi、理解当前项目、在已授权能力范围内按任务自主选择并调用 Skills/MCP、查看真实调用过程并切换模型”，不宣称服务所有用户或集成所有 Agent。

## 2. 已确认决策和设计约束

- **入口：**打开项目后优先进入真实 Pi TUI；图形辅助在旁，不以普通聊天框冒充 TUI。
- **平台与宿主方向：**建议 Windows 优先验证；用户已选择 Electron。尚未最终锁定具体依赖版本、构建器、布局验收或生产密钥存储。
- **执行核心：**优先复用用户现有 Pi 安装、认证和会话，不重写 Pi Agent loop，不安装不同版本覆盖既有 CLI。
- **项目能力：**依据当前打开项目发现 Skills/MCP，结合任务自动匹配，并在已信任、已配置且策略允许的范围内自主调用；用户可查看、固定、排除并管理授权。不能安装或启用陌生能力来假装自动化。
- **模型：**在辅助界面方便切换当前会话模型；支持 Pi 已支持的供应商、用户自定义兼容接口和中转站。模型选择必须得到 Pi 运行时确认。
- **任务点级自动路由：**新增已确认目标：依据项目任务点联合选择模型、Skills 和 MCP；先满足质量/隐私/权限约束，再优化总耗时和总成本。完整模块见 [任务路由设计](task-routing-design.md)，不把它视为 Pi 已内置的自动功能。
- **真实终端：**按 Windows PTY 接入验证计划研究 `node-pty` 与 `xterm.js`；尚未安装或完成集成。桌面侧需保留可打开系统终端使用 Pi 的能力。
- **数据边界：**Pi 原生配置/会话优先；桌面索引可重建。原型导出草稿不能直接覆盖真实 Pi 配置。

## 3. 体验原则

1. 用户先选/打开项目，再给任务；Pi 与面板显示相同的规范化项目路径。
2. 自动选择给出理由和证据（技能描述匹配、所需工具、授权来源）；匹配不确定时允许手选。
3. “已发现”“已允许”“已连接”“本任务选用”“本任务实际调用”是五种不同状态，不能用一个绿色点概括。
4. 计划中的调用可查看；真正调用由 Pi 完成，显示真实工具事件和结果。请求已接受不等于执行成功。
5. 常规、已授权工具不重复打断；新技能信任、MCP 凭据、服务器启用、外发敏感数据和扩大路径/权限时明确确认。
6. 允许范围内，Pi 可自主决定何时使用匹配的 Skill/MCP，不要求用户逐次点击；超出项目授权边界时必须停止并请求确认。匹配、授权、实际执行是不同状态。
7. 给出原生 Pi 终端入口；图形功能不可用或扩展不兼容时，指出具体边界，允许回到 TUI。
8. 开关不可表现成隔离沙箱。要限制文件、进程或网络能力，须由 OS sandbox、专用账户或容器提供实际边界。

## 4. 信息架构

- **项目：**打开/切换目录、最近项目、规范路径、信任状态、项目说明文件、能力覆盖和路径权限。
- **终端：**真实 Pi TUI、会话状态、终端字体与尺寸、系统终端打开入口。
- **能力：**Skills、MCP 工具、Pi 扩展；来源、项目适用性、权限、兼容性与本任务调用记录。
- **模型：**当前模型、可用模型、供应商/中转站配置、登录状态、上下文/工具能力及验证状态。
- **设置：**日志等级、终端、会话恢复、UI、更新与安全设置。

推荐桌面三栏：项目与会话导航 | 主 Pi 终端 | 按需展开的辅助面板。终端始终可一键聚焦；小屏将面板折叠为标签，不改变其后面的执行会话。视觉令牌和当前静态原型见 [`prototype-design.md`](prototype-design.md)。

## 5. 项目能力解析与任务路由

### 5.1 项目上下文

打开项目后，建立规范路径与 Git 根目录（若存在），识别 Pi 当前目录能发现的能力和项目文件。能力项必须附带来源层级：

- **用户级 Skills：**如 `~/.pi/agent/skills`、`~/.agents/skills`。
- **项目级 Skills：**工作目录及仓库规则覆盖范围内发现的 `.pi/skills`、`.agents/skills` 等 Pi 1.3.0 支持目录。
- **用户 MCP：**Pi 用户配置中的服务器。
- **项目 MCP：**项目 `.pi/mcp.json`，只有 Pi 的项目 trust 同意后才读取/加载。
- **扩展：**用户已安装扩展及项目扩展；可执行代码要独立显示和评估，不能假设它只是数据。

解析必须复用/核对当前 Pi 版本的发现行为；不要扫描整个磁盘或未打开的私有项目。项目 MCP 清单可显示为“待信任”，在 Pi 自己授予 trust 前不导入执行。

### 5.2 任务到 Skills 的匹配

Pi 原生已支持按名称、描述发现 Skills，并在匹配时读取完整 `SKILL.md`；用户可以显式使用 `/skill:name`。候选实现：

1. Pi 启动时公布 Skill 名称、描述和路径；工作台仅读取当前项目可见的能力目录，不复制执行说明或建立平行 Skill 执行引擎。
2. 用户提交任务后，依据任务目标、Skill 描述、项目类型及 allow/deny 策略匹配候选。只有已发现、已信任、策略允许的 Skill 才能参与自动选择。
3. 对单一且高匹配候选，在项目已授权范围内允许 Pi 原生 Skill 路由自行选择和按需读取完整 `SKILL.md`，无需用户每次点选。界面展示“候选”和“Pi 已实际载入/调用”的不同状态，不伪称桌面已执行。
4. 用户明确选择时，优先通过 Pi 原生 `/skill:name` 或已验证扩展机制交给 Pi；不能向正编辑中的终端直接注入命令。执行结果以 Pi 会话事实为准。
5. 多个同等候选、匹配不确定或策略有冲突时，由用户选择或交由 Pi 在已授权候选中判断。若为了匹配额外发起 LLM 请求，须说明请求和潜在费用，不得无提示路由。
6. 用户可按项目固定、禁用或排除 Skill；切换项目后重新解析，不沿用其他项目的私有候选。
7. 用标注任务集验证唯一匹配、多候选、无匹配、相似恶意描述、用户显式指定及未授权拒绝；分别报告推荐、Pi 实际选择/加载和任务结果，不混成一个准确率。

不得在 Electron 中自行执行 skill 文件夹脚本或重新解释 `SKILL.md`；它们可能包含提示注入、危险命令或可执行资产。

### 5.3 MCP 服务器与工具路由

把以下流程明确分开：

1. **发现：**以当前 Pi runtime 为事实源，列出当前项目可见的服务器、工具、来源、信任和连接状态；项目切换后重读，隔离不同项目能力。
2. **筛选：**先把 Pi trust、服务器启用状态与项目 allow/deny 策略求交，再匹配任务目标和工具元数据。没有匹配项时明确报告缺少工具，不凭服务器名称猜能力。
3. **自主调用：**唯一或强匹配、已配置且已授权的工具可以交由 Pi 按正常工具调用流程自行选择；无须用户每次再点确认。界面分别显示“任务候选”“Pi 实际调用”和“结果”。
4. **信任/授权：**Pi 项目 trust、访问新凭据、启用新的服务器、向远端发送敏感内容、外部写入或超出项目 allow 范围的操作，必须由相应的 Pi/桌面确认关卡处理。匹配成功绝不等于取得授权。
5. **连接：**复用 Pi 原生 MCP 生命周期与凭据配置，不在 UI 侧复制连接实现。按项目运行 Pi 的配置覆盖方式须实测。
6. **调用与记录：**从 Pi runtime 事件记录会话、server/tool、时间、真实结果/失败和授权来源；参数及结果可能含秘密，默认脱敏，细节按需显式查看。
7. **用户控制：**支持项目级固定、禁用服务器/工具和 `confirmFirst` 策略；未知/失效策略采用保守限制，不扩大权限。

**生命周期限制（Pi 1.3.0 文档）：**Pi 会在会话启动时连接所有启用的 MCP 服务器。`deferred`、`codemode` 等是工具暴露策略，不是服务器惰性启动。首阶段可按项目策略禁用不相关服务器并仅提供任务所需工具，但这可能需要按项目启动 Pi，且须实测 CLI 参数/config 覆盖。真正任务触发才拉起服务器是后续能力，需要独立会话 orchestration；不能将其伪报成现有 Pi 默认行为。

**调用规则：**用户要求“根据项目需要自己调用”，因此允许范围内的能力可以自主匹配并调用，不应变成每个工具逐次询问的审批流。项目 allow/deny/confirmFirst 与 Pi 原生 trust、认证及工具权限共同约束此自主行为；外发敏感数据、外部写入和越出范围动作须停下来确认。Pi 1.3.0 会话启动时连接的是启用服务器；按任务路由工具不等于按需启动服务器进程。

### 5.4 项目策略数据

可考虑在工作台项目元数据中存储策略，字段与落盘格式尚未定版：

| 概念 | 设计语义 |
|---|---|
| 策略版本 | 未知版本不自动放行，提示迁移或人工处理 |
| Skills 允许/拒绝/固定 | 限制候选来源并保留用户选择；不把文本规则当执行隔离 |
| MCP server/tool 允许和拒绝 | 拒绝优先；限制精确到工具和必要的参数范围 |
| 必须确认的动作 | 指定需逐次确认的调用，确认绑定会话、项目与调用参数 |
| 数据披露范围 | 记录允许发送的数据类别与目的服务；超出范围重新确认 |

该策略不是 Pi 自带 schema，也不是现成可执行配置。它只能收紧已授权能力，不包含凭据、不授予 OS 权限、不覆盖 Pi trust。项目共享策略与个人授权应区分；仓库内容不能自行授予新增权限。

### 5.5 执行层限制与可观察性（必须先验证）

- Pi 1.3.0 类型声明明确：`setActiveTools()` 控制模型声明的活动工具集，但 `codemode`/`deferred` 工具即便不活动，仍可能从 codemode 调用。因此从 UI 隐藏或移出 active 列表不是 deny 的执行保障。
- 项目拒绝规则应在实际 `tool_call` 执行路径核验，并测试直接调用、codemode 间接调用、嵌套调用及 resource 读取。当前只是实现要求，尚无拦截验证。
- MCP 的 `readOnlyHint`、`destructiveHint` 等是服务器声明的未验证提示，不足以自动授予权限；还要结合可信工具定义、参数、目标服务及用户授权。
- trust 不等于沙箱；Pi 内置 read/bash 等工具可能绕开“禁止某 Skill”的界面规则去读文件或执行动作。若要求强隔离，须评估 OS 权限或沙箱，不能把路由偏好包装为访问控制。
- Skill 是工作指导，不一定对应一个独立执行事件。只有读到实际文件访问、显式 Skill 命令展开或可验证事件时，才能说“已加载”；加载不证明模型遵守了全部步骤。无法观测时显示未知。
- 如用户已有 `/mcp` 替代扩展，Pi 内置 MCP 行为可能被替换；探测实际实现后选择对应适配，不能混用原生文档推断运行状态。

## 6. 真实终端与图形辅助架构

```text
Electron 主进程（生命周期、受限 IPC、项目路径授权）
        │ 管理受监督的 Pi 子进程与 Windows ConPTY
        ├────────────── Pi TUI ───────────────┐
        │       Pi 会话 / Skills / MCP / tools │
        │                                      │
        └─窄接口 IPC─终端视图(xterm.js) + 图形辅助面板
                     项目能力状态 / 模型候选 / 调用观察
```

- Electron 主进程管理受监督的子进程退出、重启和窗口生命周期；renderer 不获得任意 Node.js、shell 或文件系统 IPC。
- React/Vue 尚未确认；本项目当前没有 UI 框架锁定。本蓝图不擅自加依赖。
- PTY 负责交互式 TUI 的终端协议；如果 TUI 被系统终端独占运行，辅助 UI 可采用观测/控制适配，不直接共享写入。
- **同一 Pi 会话一次只有一个输入写入者。** 原生终端可以在进程不变时隐藏/展开；换到另一个终端恢复会话则须先结束或明确交接原执行者，不能称为活进程无损迁移。应用租约不足以约束外部 CLI，不能自动抢夺会话。
- 关闭窗口要明确区分“仅关窗口，Pi 继续运行”与“终止 Pi”。首版取决于进程监督验证；不得默认后台持久承诺。
- 不解析 ANSI 字符序列猜工具状态、权限或模型切换成功；可靠状态来自 Pi 正式 API/扩展。
- IPC 限制为项目选择、会话生命周期、terminal resize/input/data、显式能力/模型请求及事件流，校验长度、序号和会话代次。

## 7. 快速模型切换与中转站

Pi 原生支持 `/model`、`Ctrl+P`、`/scoped-models`。Pi 1.3.0 RPC 有 `get_available_models` / `set_model`；扩展 API 有 `ctx.modelRegistry`、`setModel(model)`，凭据缺失会返回失败。

按原生终端优先约束：

- 首版保留 Pi 原生快捷键与 `/model`，图形侧只显示已验证的当前模型。
- 图形选择应用到当前 TUI 的机制必须用该版本扩展 API 验证，不能通过随意注入文本打断用户输入。
- 中转站使用 Pi 支持的 endpoint 协议优先写入/合并 `models.json`，API Key 采用系统凭据、环境变量或 Pi 的登录机制；原型里的 `${VAR}` 草稿不自动等于 Windows 运行时已有环境变量。
- Pi extension 可 `registerProvider()`、切换模型；若提供项目外的动态 provider bridge，应独立记录风险与失效行为。
- 每个 endpoint/model 显示 API 类型、能力、模型 ID 来源和“未验证/已通过基准请求”状态；兼容 API 宣称不替代实际测试。
- 生成式自动换模型如果增加 LLM 调用或请求，必须提示费用和授权；首版不做无提示路由。
- 不覆盖用户 `auth.json`、原生模型配置未知字段或 session 选择。提供显式预览、备份/回滚、原子写入方案再进入实现。

### 7.1 按任务点自动选择模型

用户最新要求已纳入：不只手动切换，要根据项目各任务点自动选择适合的模型，同时匹配 Skills/MCP，形成可验收执行方案。先在用户已批准模型/工具集合内过滤凭据、模态、工具能力、上下文、隐私、预算，再用项目任务评测决定质量门槛和成本/耗时取舍。

首阶段建议影子推荐，验证后在任务点安全边界自动应用；不在未完成模型请求/工具调用中途切换，不通过 PTY 注入 RPC 命令。保留人工锁定、失败升级和预算停止；升级不能重放结果未知的外部副作用。界面区分候选、Pi 实际活动模型及验收结果。详细方法、方案比较、异常和验收见 [task-routing-design.md](task-routing-design.md)。目前没有最优模型或降本/提速的实测结论。

## 8. 安全与隐私模型

- **信任是分层授权：**应用打开项目 ≠ Pi 项目 trust ≠ 安装扩展 ≠ 访问远端 MCP ≠ 访问更多文件。
- 首次打开目录显示规范路径和即将加载的项目设置、MCP、Skills、扩展；支持只读浏览/跳过，交由 Pi 原生 trust 最终确认。
- Electron 使用沙箱和 context isolation，renderer 不加载任意远程内容，不暴露通用 exec/path IPC；外部链接使用系统浏览器并限制协议。
- 扩展、MCP 服务与 skills 包可能执行代码；按来源和能力展示，首次安装/启用确认。提示不替代 OS sandbox。
- 不记录 API Key、OAuth token、完整认证头、未脱敏请求、未经同意的文件正文。调试日志在界面默认脱敏。
- 本机 HTTP 监听不是默认架构；若后续采用，限制 loopback、鉴权与 CSRF/Origin 校验，端口必须登记并验证。
- 默认本地控制。远程控制、共享、云同步及多用户运行属于单独威胁模型，不在首版隐含支持。

## 9. 首版范围与明确不做

### 纳入开发验证

1. Windows Electron 壳启动已存在的 Pi 1.3.0/可配置 Pi 命令，直接 PTY 显示真实 TUI。
2. 中文输入、快捷键、终端 resize、退出处理；有系统终端 fallback。
3. 项目切换以及只读能力索引：列出当前项目/用户 Skills 和 MCP 来源、trust/启用状态。
4. 在项目授权集合内按任务自主选择/调用已配置 Skills/MCP，显示匹配理由；用户可固定、排除、禁用；由 Pi 运行时核实实际选择与调用。
5. 展示模型与 Pi 原生命令；经过验证的图形快捷切换试验。
6. 中转站配置草稿、安全合并流程设计，不写明文 secret、不覆盖原配置。
7. 任务点级模型/Skills/MCP 联合路由：先只推荐并比较固定模型基线，验证安全切换后再开启受控自动应用与验收升级闭环。

### 明确延期

- 任意项目技能/扩展的自动安装、任意 MCP 自动连接。
- MCP 服务器每工具按需冷启动、跨平台原生沙箱、远程桌面。
- Claude Code/Codex/Grok/Trae 引擎直接共用 Pi 会话。
- 多 Pi 写同一 session、自动批准危险动作、后台永续承诺。
- 商业发行、签名自动更新、公开插件市场。

## 10. 验收矩阵

| 类别 | 必验情形 | 通过依据 |
|---|---|---|
| 原生终端 | Pi 启动、中文输入法、复制粘贴、快捷键、缩放/resize、超长输出、图形/图片提示 | 和系统终端对照可运行；不丢输入，不伪造输出 |
| 项目解析 | 用户级与多个项目 Skills、仓库根祖先发现、项目切换 | 能说明来源与冲突；不泄漏另一个项目能力 |
| Skill 自动选用 | 强匹配、弱匹配、多 skill、明确 `/skill:name`、模型漏选 | 本地固定测试集中匹配正确；用户能覆盖，未授权 skill 不执行 |
| MCP trust | 无信任、有信任、拒绝信任、同名覆盖、失效密钥、服务器失败 | trust 前不加载项目 MCP；状态清楚，失败不伪报成功 |
| MCP 按项目路由 | 多个项目不同 MCP；模型选择工具/用户指定/无匹配；服务器初始化 | 仅显示当前策略允许工具；实际调用和服务器启动分别记账 |
| MCP 自主调用 | allow/deny/confirmFirst、唯一匹配、多候选、无匹配、远端读、外部写 | 在授权集合内由 Pi 自主选工具；越界停止/确认；区分推荐、真实调用、服务器连接 |
| 生命周期 | 未决对话、关窗、退出、Pi 崩溃、外部 Pi 并发打开 | 用户输入安全；状态可恢复或明确中断；不双写同会话 |
| 模型 | 可用凭据、缺凭据、切换成功/拒绝、未知 ID、端点不兼容 | 确认运行时 model change 才显示成功，原生配置可恢复 |
| 任务点自动路由 | 模型/Skill/MCP 联合能力、隐私过滤、手动锁定、预算不足、安全切换、验收失败升级 | 以任务质量与总耗时/费用对照评测；不绕过授权，不重放未知副作用，候选不伪报为实际模型 |
| 安全 | 恶意项目内容、秘密 key、扩展/MCP 未信任、路径与 IPC 越界 | 没有越权读写；日志和截图无 secrets；危险情形明确提示 |
| 性能 | 首屏、pty event→paint、终端高流量、内存/CPU 与原生 TUI 对照 | 固定机器/版本/样例和重复次数后报告分布；尚无基线，不预设数字 |

## 11. 分阶段计划

1. **技术可行性验证：**创建隔离子项目，安装核准版本；验证 Electron ↔ xterm.js ↔ PTY ↔ 用户已有 Pi，先跑无模型会话与非敏感任务。
2. **观测与退出：**增加窗口状态、日志脱敏、异常退出提示、系统终端 fallback。
3. **能力索引：**读取 Pi 已发现的 Skills/commands/MCP tools 与项目 trust；没有文件修改，先只读。
4. **按项目自主调用：**应用 allow/deny/confirmFirst 策略，固定任务集分别验证 Skill/MCP 推荐、Pi 实际调用及结果。
5. **图形控制：**按 Pi 1.3.0 扩展 API 验证模型切换或 RPC 查询，确定真实 TUI 下的桥接方法。
6. **联合路由：**按任务点做影子推荐和保留测试集评测；安全切换验证通过后，再做模型/Skills/MCP 自动选用与有限升级，统计完整任务质量与总费用。
7. **真实性能与打包：**与原生终端对照，完成隐私/许可/签名审查后再做公开发行方案。

首版建议不引入数据库。若第一版仅 Electron IPC 管理本地 PTY，不需要前后端 HTTP 端口；如后来确实引入服务，再按项目 README 和活跃监听分配端口。

## 12. 当前决定

用户已选定“打开就是真实 Pi 终端，旁边有图形辅助”、Electron 方向，并明确要求按项目需要自主调用 Skills 和 MCP。早期“原生终端还是图形优先”“技术栈未确认”等调研问题已经有答案，权威决策以本蓝图及 [`decisions.md`](decisions.md) 为准。项目级自动选择是已确认的产品目标，具体界面、策略文件格式和自动匹配精度仍须原型/实现验证。

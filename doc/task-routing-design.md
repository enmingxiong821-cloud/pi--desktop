# 任务点级智能路由：模型、Skills 与 MCP 联合选择

## 1. 需求与交付边界

用户新增要求：依据项目的具体任务点自动选择合适模型，高效、高质量完成任务；Skills 与 MCP 同样按项目所需自动调用。

这是已确认的产品目标，不是已实现能力。本文仅交付模块设计，不引入依赖，不改变 Pi 配置，不执行模型或工具请求。原生 Pi TUI＋Electron 辅助的方向不变。

**目标定义：先满足质量、安全、兼容性和隐私约束，再优化完成任务的总耗时与总成本。** 不能同时无条件保证最高质量、最低成本和最快速度；模型“更贵”“名字更新”也不构成更适合当前任务的证据。

## 2. 路由单位：可验收的任务点

一个项目分解成有依赖、输入、产出和验收标准的任务点，而不是每句话、每个 token 都换模型。简单目标可只有一个任务点，不强制调用额外规划模型。

每个任务点至少描述：

| 信息 | 用途 |
|---|---|
| 任务 ID、项目、依赖与当前状态 | 防止不同项目/阶段混用能力和重复执行 |
| 目标、输入范围、预期产出 | 明确要做什么，不仅按关键词分配 |
| 任务类型和复杂度证据 | 如资料查找、局部修改、跨模块实现、根因分析、审查；分类不是品牌排名 |
| 风险与数据分类 | 是否涉密、允许发送到哪些供应商/MCP、是否产生外部副作用 |
| 所需能力 | 工具调用、图片输入、输出格式、上下文容量及必要 Skills/MCP |
| 验收标准与检验方法 | 测试、编译、引用核查、变更评审或人工确认；通过条件先于执行 |
| 成本/时间偏好与剩余预算 | 限制路由、执行、复核、重试的总开销 |

任务图建议在原生 Pi 会话内串行执行有写入的任务点；独立只读任务是否并行属于后续设计。不得为了自动路由同时启动多个进程写同一会话或同一文件。

## 3. 输入、输出与模块职责

### 输入

- 当前项目上下文和任务点，已批准的项目策略与数据披露范围。
- Pi 当版本实际可用的供应商/模型目录及认证状态。
- 当前项目已发现的 Skills 和已配置、可信的 MCP 服务器/工具。
- 有来源与时间戳的能力资料、任务评测结果、费用资料、限流/错误记录。
- 用户锁定的模型、禁用项、自动路由模式与预算。

### 输出：一份执行方案

输出不是单个模型名，而是“任务点 → 候选/选定模型与供应商端点 → Skills → MCP tools → 授权要求 → 验收方案 → 备用路径”。同时给出简短选择理由、证据来源、不确定性、费用估计及安全切换时机。

推荐、应用、执行和验收分别有状态；只有 Pi 确认后才能显示已切换/已调用，验收通过后才能显示任务点完成。不展示或索取模型隐藏思维过程。

### 联合选择，不是三个互不相关的选择器

先从任务推导必要技能和工具能力，再筛选可承载这些能力的模型。例如任务需要图片和工具调用，就不能仅因某模型延迟低而选择未验证这些能力的端点。反过来，模型能力或预算不足时也不能偷偷删掉必要工具来“完成”任务，应调整计划或请求用户决定。

## 4. 模型能力登记与硬约束

模型目录不能只保存供应商品牌。路由记录应区分模型 ID、供应商、实际端点/中转站、协议、版本或别名、能力来源与最近验证时间。

选择前过滤：

1. 用户是否允许该模型/供应商，以及当前凭据是否可用。
2. 项目资料和会话历史是否允许发送给目标端点；跨供应商可能发送此前工具结果与文件内容，不只是新任务一句话。
3. 所需输入模态、工具调用、结构化输出、上下文与输出预算是否支持并经过适当核验。
4. 端点健康、限流、实际服务别名与已知协议兼容性；中转站目录声明不替代实际验证。
5. 用户剩余预算、时间要求及最低质量门槛。

没有符合硬约束的模型时，说明缺少什么并停止自动执行；不能绕过数据限制、降低质量门槛或默默增加预算。仅有一个可用模型时继续使用它并说明没有切换收益证据。

未知价格不视作免费；未知能力不视作支持；模型自述“很擅长”不当作评分。对于尚未评测的模型，采用用户确认的保守默认模型/人工选择，而不是虚构质量分数。

## 5. 路由方法比较与推荐

| 路线 | 优点 | 成本与边界 | 本项目建议 |
|---|---|---|---|
| 项目规则＋能力过滤＋本地任务评测 | 可解释、容易复现，规则命中时不需要额外模型调用 | 规则维护与任务集标注；复杂边界需人工处理 | 第一阶段，先影子推荐后开启受控自动应用 |
| 学习型/语义分类路由 | 可利用任务差异及历史评测信号 | 需要校准、评估分布漂移；分类器/embedding 可能产生额外成本和数据外发 | 第二阶段候选，不自动安装 RouteLLM 等依赖 |
| 网关侧跨模型路由 | 可集中管理端点、预算、故障切换 | 增加服务、运维、秘密与隐私边界；Pi 可能只看到虚拟模型别名 | 可选高级集成，需能追溯实际服务模型，不作为首版必需 |

建议优先“硬约束过滤 → 质量门槛 → 预期总成本/耗时比较 → 稳定性/可用性校验 → 执行”。质量置信度与评分阈值通过项目相似任务校准，不在资料阶段编造固定权重、成功率或降本百分比。

允许模式建议：

- **质量优先：**在预算和隐私范围内选有证据满足更严格验收的候选；必要时增加经授权的独立复核。
- **均衡：**满足该任务质量门槛后优化总耗时/费用，计入重试与交接。
- **速度优先：**在相同最低质量门槛下偏重端到端时间；不能把跳过测试当作提速。
- **手动锁定：**固定当前任务点、会话或项目的模型；自动路由不能覆盖用户锁定。

模式名称、默认值与预算数值待用户确认。先做“只推荐、不切换”的影子模式，再用受控测试决定是否默认自动应用。

## 6. 联合路由流程

项目和任务输入 → 明确任务点/验收标准 → 读取项目授权策略 → 匹配必要 Skills/MCP → 过滤模型候选 → 比较质量/总开销 → 生成执行方案 → 在安全边界应用 → Pi 执行 → 验收 → 继续/修订/升级/停止。

关键规则：

- 使用 Pi 已发现的 Skill 名称/描述，按需读取全文；没有证据时不声称加载或遵守。
- MCP 候选必须符合原生 trust 与项目策略，deny 优先；权限在实际工具执行路径检查，不能仅隐藏 UI 或修改 active-tools。
- 工具服务器的 readOnly/destructive 等 annotations 只能作为未验证提示，不能自动授权。
- 匹配规则、模型输出、项目文件或 MCP 返回内容都不能扩大许可范围、开启额外供应商或提高预算。
- 能力缺失时报告缺口；如建议安装/启用新 Skill、扩展或 MCP，须另获授权，不属于默认自主调用。
- Pi 1.3.0 会话连接启用的 MCP 服务器；按任务筛工具不等于按任务启动服务器。此生命周期边界继续有效。

## 7. 安全切换和上下文交接

自动路由以任务点边界为主，避免频繁换模型导致上下文与提示缓存重建。是否真的损失缓存取决于供应商与协议，应测量而非一概认定。

- 切换前等待 Pi 可确认的空闲/安全边界：没有未完成的模型请求、tool call/result 配对、待答授权问题或状态不明的副作用操作。
- 已排队输入要绑定正确任务点和执行代次，不跨任务静默改归属。
- 整理必要的任务目标、已确认决定、变更文件、实际工具结果、未决问题和验收结果；摘要必须保留证据引用。不得把模型推测混成已完成事实。
- 估算目标端点可接收的完整有效上下文，核查历史图片、tool schema/调用 ID、推理块、加密状态和格式兼容；不能假定跨供应商无损恢复。
- 只在原生 TUI 的 Pi 扩展桥验证通过后使用当前版本模型切换 API；RPC 命令只属于 RPC 模式，不能直接发进 TUI PTY，也不能用第二个 RPC 进程同时控制同一会话。
- Pi 确认当前活动模型后再开始下一任务点；失败时保留原状态、提示原因，不把 UI 候选写成已生效模型。
- 如确需新会话/分支，显式提示并获得相应选择，不静默分叉、丢失历史或后台启动平行写入者。

## 8. 预算、失败分类与升级

预算包含规划/分类、输入/输出、上下文重发、执行、复核、失败请求与重试；自定义中转价采用用户提供的报价并注明来源，实际账单仍可能与估算不同。

| 失败类型 | 行为 |
|---|---|
| 质量验收不通过 | 先定位失败证据；允许范围内修正方案或切换有评测依据的更合适模型；限制重复次数与总预算 |
| 工具/权限/环境失败 | 修复环境或请求权限；不把它直接归因于模型弱，也不盲目升级模型 |
| 认证失败、端点限流或不可用 | 在同等能力/隐私约束的已批准备用候选中选择；无可用项则停下 |
| 上下文不兼容/超限 | 计划可审查的交接摘要或合适候选；不得默默截掉验收约束、关键结果或权限信息 |
| 副作用结果未知 | 先检查外部真实状态/幂等性，禁止因换模型而重放发布、写入、支付等操作 |
| 剩余预算不足 | 展示已耗费、估算与可选方案，暂停或请求追加；不得自动提高额度 |

需设计调用前的预算预留及调用后的结算修正；并发/在途请求费用可能延迟返回，未知收费不能归零。无法保证供应商侧严格金额上限时必须说明限制，不能宣称本地计数等于供应商硬预算。

升级要有次数/时间上限、去重及冷却，避免在两个模型间来回切换。验证器、独立 reviewer 和额外请求均计费且受授权约束；不默认让多个模型重复做每个任务。模型复核意见也不是独立正确性证明。

## 9. 图形辅助交互

侧栏展示当前任务点、路由模式、候选/实际模型、选用理由、候选 Skills/MCP、权限与预算状态；展开后看脱敏调用和验收证据。

用户可：手动锁定模型、限制供应商/工具、暂停自动路由、修改预算、拒绝新数据披露、接受/拒绝升级建议。变更策略的生效范围清楚区分“本任务点/本会话/本项目”。

状态建议：待分析 → 方案候选 → 待授权（如有） → 待安全切换 → Pi 已确认 → 执行中 → 验收中 → 通过/需修订/受阻/取消。没有实际路由或 Pi 证据时显示“未验证”。

## 10. 验收与评估方法

用脱敏、可重复、贴近实际项目的任务集；训练/调参任务与保留测试任务分开，按项目/任务类型分组防止泄漏。用模拟响应测试路由/权限机制，再在用户批准预算下进行真实模型对照。

| 维度 | 必验内容 |
|---|---|
| 功能正确 | 唯一/多个/零模型候选；只有一个模型；人工锁定；手动覆写；Skill/MCP 联合能力约束 |
| 权限隐私 | 私有项目只允许指定端点；历史会话含敏感工具结果；恶意任务/工具描述要求扩权；deny/confirmFirst；项目切换隔离 |
| 上下文切换 | 未完成 tool call、queued input、长历史、多模态、切换失败、无认证、协议/缓存差异 |
| 质量 | 编译/单元/接口/浏览器验证等适用检查；任务验收率、返工率、人工评审；非代码任务使用引用/内容核查 |
| 总开销 | 整个任务完成时间、总 token/实际或估计账单、分类与复核成本、失败和重试、缓存影响 |
| 故障 | 限流、超时、认证失败、预算不足、价格未知、重复升级、外部副作用状态未知 |
| 证据 | 推荐与实际活动模型一致；工具真实调用可追溯；未调用/未验证项不得标成功 |

基线至少包括固定用户默认模型、固定有代表性的高能力候选、规则路由和拟采用的自动策略。保持任务、配置和验收相同并重复测量，记录失败及中止案例，不只报告成功样本的费用。

不以公开 benchmark 排名替代项目任务评测，不从 RouteLLM/LiteLLM 的研究数字推导本产品节省比例。当前没有项目路由性能、质量或成本的实测结果。

## 11. 参考与开发顺序

- RouteLLM：[仓库](https://github.com/lm-sys/RouteLLM)、[作者研究说明](https://lmsys.org/blog/2024-07-01-routellm/)。借鉴成本/质量曲线与阈值校准；原研究模型对、问答评测不自动等于当前 Pi 工具型任务表现。部分路由器需远程 embedding，额外隐私与费用要评估。
- LiteLLM：[部署路由](https://docs.litellm.ai/docs/routing)、[Auto Router](https://docs.litellm.ai/docs/auto_router/)。区分部署均衡/故障恢复与语义任务路由；网关是可选参考，不直接纳入本项目依赖。
- 本机 Pi 1.3.0 模型/扩展依据见 [来源登记](sources.md)。只有已核准的 Pi API 能用于真实 TUI 桥。

推荐先做任务点和能力目录 → 只推荐的影子路由 → 固定测试集比较 → Pi 安全切换验证 → 已批准策略内自动应用 → 有预算上限的验收升级闭环。实现仍以方案确认为前提再开展。
